Bluetooth & Account Pairing Architecture

End-to-end map of how an offline AIOS box gets onto Wi‑Fi via encrypted BLE (with a remembered provisioning key), then binds to a user account through LAN + aios-cloud, and stays reachable via relay and Cloudflare Tunnel.

1. System overview

Three actors. Phone ↔ box over BLE for Wi‑Fi (and later reprovision). Phone ↔ box over LAN HTTP for account pairing. Box ↔ cloud over HTTPS claim + WSS relay. Off-LAN the phone hits the box through Cloudflare Tunnel.

2. Two pipelines — do not conflate

BLE “claim” is Wi‑Fi / crypto identity (mint provisioning_key). Account claim is POST /pair → cloud /device/claim/complete. Unpairing an account does not wipe the provisioning key.
Pipeline Channel Purpose When
A — BLE Wi‑Fi provisioning Bluetooth LE GATT + app-layer crypto (bluez-peripheral) Get box online; remember phone↔box key for moves Boot offline, or AIOS_FORCE_PROVISIONING / factory-reset
B — Account pairing mDNS / BLE LANIP + LAN HTTP + cloud HTTPS/WSS + tunnel Bind box to a user account After box is online

3. Pipeline A — BLE Wi‑Fi provisioning

Transport is plain BLE. Security is in the payload: X25519 ECDH + HKDF + AES-256-GCM on first claim; afterwards the shared provisioning_key seals new Wi‑Fi creds with no ECDH. Stack: bluez-peripheral (not bless). Prefers USB dongle over Jetson onboard MAC.

GATT surface

Service  7A71E000-1111-2222-3333-123456789ABC
├── CREDS       …E001  write   ← {"mode":"claim"|"reprovision","phonePub"?,"blob"}
├── STATUS      …E002  notify → credentials_received | connecting | connected | failed:<reason>
├── PUBKEY      …E003  read   → box ephemeral X25519 pubkey (hex) [first claim]
├── CHALLENGE   …E004  read   → fresh 16-byte nonce (hex), regenerated every read
├── DEVICE_INFO …E005  read   → {"device_id","claimed":bool,"slug"}
├── KEYOUT      …E006  read   → provisioning_key sealed under session key [first claim]
├── LANIP       …E007  read   → box LAN IPv4 once joined (skip mDNS for /pair)
└── NETWORKS    …E008  read   → [[ssid, signal, secure01], …] visible Wi‑Fi list

4. Claim vs reprovision

mode=claim

First time / factory-reset

Box has no stored key. Phone does ECDH with PUBKEY, writes phonePub + sealed blob. Box mints provisioning_key, exposes it on KEYOUT. Both sides persist it.

mode=reprovision

Moved to a new network

Phone matches device_id via DEVICE_INFO, loads stored provisioning_key, encrypts new SSID/password with it (no ECDH / no phonePub). Box rejects with failed:not_claimed if no key. Does not remint KEYOUT.

BLE state machine

stateDiagram-v2
  [*] --> ADVERTISING
  ADVERTISING --> CREDENTIALS_RECEIVED: CREDS decrypt OK
  ADVERTISING --> ADVERTISING: bad_payload / bad_mode / auth / not_claimed
  CREDENTIALS_RECEIVED --> CONNECTING: nmcli start
  CONNECTING --> CONNECTED: online · set LANIP · maybe KEYOUT
  CONNECTING --> ADVERTISING: failed incorrect_password / network_not_found / …
  CONNECTED --> [*]: hold 2.5s for KEYOUT/LANIP reads → stop BLE → FastAPI

Failure STATUS reasons include failed:bad_payload, failed:bad_mode, failed:not_claimed, failed:auth, failed:incorrect_password, failed:network_not_found, or truncated nmcli error.

5. Pipeline B — Account pairing

After Wi‑Fi, the app finds the box via mDNS, BLE LANIP, or cloud-reported lan_ip from the relay heartbeat. It hands a short-lived pairing code over the LAN; the box redeems it with the cloud and mints local_token.

6. Tokens & identity

Four auth planes: BLE session crypto (first claim), provisioning_key (Wi‑Fi moves), local_token (app↔box HTTP), device_token (box↔cloud WSS).

ArtifactWho mintsLifetimeUsed for
device_id Box (SQLite) Forever (survives factory-reset) BLE name, DEVICE_INFO, mDNS TXT, claim
provisioning_key Box on first BLE claim Until factory-reset Re-encrypt Wi‑Fi on move; not account auth
pairing_code Cloud Short / one-shot Bind box ↔ user
device_token Cloud Until unpair Box → cloud WSS
local_token Box Until unpair Phone → box HTTP Bearer (LAN, tunnel, gateway)
connector_token Cloud Until unpair cloudflared

7. Post-pair runtime topology

Same local_token works on LAN and through the tunnel. Chat is HTTP+SSE (/message) + gateway sessions — the box no longer exposes a local /ws. Cloud can still push unpair over the outbound relay.

8. Unpair vs factory-reset

PathAuthClearsKeepsSide effect
POST /unpair local_token or relay unpair device_link, tunnel device_id, provisioning_key Fast LAN re-pair; phone can still reprovision Wi‑Fi
POST /factory-reset local_token device_link + provisioning_key device_id only Sets AIOS_FORCE_PROVISIONING=1, os.execv relaunch → fresh BLE claim

9. Boot → pair storyboard

Offline → online → claimed. BLE gets you on the network (and remembers the phone); pairing code binds ownership; tokens unlock ongoing control.
